1. Executive Summary
--------------------
ScaffoldPM is an AI-driven backend system designed to help project managers
convert a project scope document into an organized and optimized project plan.
The system accepts a PDF, DOC/DOCX, or TXT scope document along with project
metadata such as project name, start date, end date, and team members. It then
extracts the document text, uses a large language model to generate a detailed
work breakdown structure (WBS), assigns tasks to suitable team members using
semantic skill matching, estimates task duration using a trained machine
learning model or fallback heuristic logic, schedules tasks based on
dependencies and team availability, analyzes the critical path, and stores the
final project plan in a SQLite database.

The system is implemented as a FastAPI backend and uses asynchronous SQLAlchemy
for database access. It includes modules for document extraction, WBS
generation, task-member matching, duration prediction, scheduling, critical
path method analysis, and project CRUD operations. The current repository
contains the backend implementation and an empty frontend directory reserved
for a future client interface.


2. Background
-------------
Project planning is a critical activity in software development and other
engineering domains. A project manager must understand the scope, divide work
into manageable components, allocate tasks to suitable team members, estimate
effort, prepare a realistic schedule, and monitor progress. These activities
are often time-consuming and error-prone, especially when project requirements
are provided as long unstructured documents.

Traditional project management tools usually require manual entry of phases,
tasks, dependencies, assignments, and schedules. ScaffoldPM addresses this
problem by using AI and automation to transform a scope document into a
structured project plan. It combines natural language processing, large
language models, machine learning-based duration estimation, semantic skill
matching, and graph-based critical path analysis to reduce manual planning
effort.


3. Problem Statement
--------------------
Manual project planning requires significant time, experience, and attention.
Project managers must read lengthy scope documents, identify deliverables,
divide the work into phases and tasks, assign each task to the right person,
estimate effort, arrange tasks according to dependencies, and detect critical
activities that directly affect the project deadline.

This manual process can cause several issues:

- Important tasks may be missed while reading the scope document.
- Task dependencies may be defined incorrectly.
- Work may be assigned to team members without considering their skills.
- Duration estimates may be inconsistent or biased.
- Project delays may occur when the critical path is not identified early.
- Project data may not be stored in a structured format for later tracking.

ScaffoldPM solves these issues by automating the initial planning workflow and
producing a structured project plan from a scope document.


4. Aim
------
The aim of ScaffoldPM is to design and implement an AI-driven project planning
system that automatically generates, optimizes, and stores a structured
software project plan from an uploaded scope document.


5. Objectives
-------------
The main objectives of ScaffoldPM are:

1. To extract readable text from uploaded project scope documents.
2. To generate a detailed work breakdown structure using an LLM.
3. To divide a project into phases, activities, and tasks.
4. To identify task skills, task types, and dependencies.
5. To assign tasks to team members based on skill similarity and workload.
6. To estimate task duration using a trained ML model or fallback heuristic.
7. To schedule tasks using dependencies, working days, and member availability.
8. To compute task slack and identify critical path tasks.
9. To store generated project plans in a relational database.
10. To provide APIs for retrieving projects, listing projects, updating task
    status, and changing task assignment.

17. Main Workflow in Detail
---------------------------
Step 1: Request Validation
- The user sends a multipart request containing a scope document and a JSON
  payload.
- The payload is parsed and validated using Pydantic.

Step 2: Document Text Extraction
- The uploaded file is inspected using filename extension and content type.
- PDF files are processed using pdfplumber.
- If pdfplumber cannot extract text from a page, PyMuPDF is used as fallback.
- DOC/DOCX files are processed using python-docx.
- TXT files are decoded using UTF-8 or Latin-1 fallback.
- Extracted text is cleaned by removing repeated headers, repeated footers,
  page numbers, and unnecessary whitespace.

Step 3: WBS Generation
- The cleaned scope text, project details, and team member data are sent to an
  LLM through LangChain.
- The prompt instructs the model to create 4 to 6 phases.
- Each phase should contain 3 to 6 activities.
- Each activity should contain 4 to 8 tasks.
- Every task should include title, description, type, required skills, and
  dependencies.
- The output is parsed into Pydantic models.
- If parsing fails, the system retries once with a stricter instruction.

Step 4: Dependency Resolution
- The LLM returns dependencies as task titles.
- The system normalizes task titles and maps dependency titles to generated
  task IDs.
- Dependencies that cannot be matched are ignored.

Step 5: Task Assignment
- Team member profiles are created from role, skills, and experience.
- Task profiles are created from title, description, task type, and required
  skills.
- SentenceTransformer converts profiles into embeddings.
- Cosine similarity is computed using normalized embeddings.
- Assignment score considers semantic similarity, team member experience, task
  complexity, and current workload.
- More complex tasks prefer more experienced members.
- Load penalty prevents assigning too many tasks to the same person.

Step 6: Duration Estimation
- The system tries to load duration_model.pkl.
- If the trained model exists, it predicts estimated hours.
- If the model does not exist, a heuristic estimate is used.
- Heuristic estimation considers task type, assignee experience, number of
  required skills, and description length.
- Duration is clamped between 2 and 40 hours and rounded to the nearest 0.5
  hour.

Step 7: Scheduling
- Tasks without dependencies are placed in the ready queue first.
- Tasks are selected based on earliest feasible start date.
- A task can start only after its dependencies are finished.
- A task can start only when its assigned member is available.
- Estimated hours are converted to working days using 8 hours per day.
- Weekends are skipped.
- Each task receives a start_date and end_date.

Step 8: Critical Path Analysis
- A directed graph is created where nodes are tasks and edges are dependencies.
- NetworkX performs topological sorting.
- The system calculates earliest start and finish times.
- The system calculates latest start and finish times.
- Slack is calculated as latest start minus earliest start.
- Tasks with zero slack are marked as critical.
- The API returns a list of critical task IDs.

Step 9: Persistence
- Team members are inserted if they do not already exist.
- Project, phases, activities, and tasks are saved.
- The generated plan can later be fetched by project ID.


18. Algorithms Used
-------------------
1. Text Extraction and Cleaning
- Removes repeated headers and footers.
- Removes page numbers.
- Reflows broken lines into paragraphs.
- Keeps headings and list items readable.

2. LLM-Based WBS Generation
- Uses prompt engineering and Pydantic output parsing.
- Converts unstructured scope text into structured planning data.

3. Semantic Skill Matching
- Uses all-MiniLM-L6-v2 embeddings.
- Computes similarity between team member profiles and task profiles.
- Adjusts score using experience multiplier and workload penalty.

Formula concept:
final_score = (semantic_similarity * experience_multiplier) / load_penalty

4. Duration Estimation
- ML model: XGBoost regression.
- Features:
  - task type value
  - description word count
  - required skills count
  - assignee experience value
  - heuristic hour estimate
- Target:
  - actual task hours from the dataset.

5. Greedy Scheduling
- Uses task dependencies and member availability.
- Chooses ready tasks by earliest feasible start.
- Updates member availability after scheduling a task.

6. Critical Path Method
- Uses directed acyclic graph logic.
- Calculates earliest start, earliest finish, latest start, latest finish, and
  slack.
- Critical tasks are tasks with zero slack.

20. Heuristic Duration Estimation
---------------------------------
When the trained model is not found, ScaffoldPM uses rule-based estimation.

Base hours:
- feature: 16 hours
- bugfix: 6 hours
- documentation: 4 hours
- research: 12 hours
- other: 8 hours

Experience factor:
- junior: 1.2
- mid: 1.0
- senior: 0.85

Additional factors:
- Skills factor: number of required skills up to 6 multiplied by 1.5.
- Text factor: description word count up to 300 words divided by 100 and
  multiplied by 0.8.

Final value:
- Clamped between 2 and 40 hours.
- Rounded to the nearest 0.5 hour.


21. Scheduling Rules
--------------------
- Working day means Monday to Friday.
- Saturday and Sunday are skipped.
- One working day equals 8 hours.
- Task duration in days is ceiling(estimated_hours / 8).
- A task with no estimated hours receives a default duration of 1 day.
- A dependency task must finish before the successor task begins.
- A team member cannot work on two assigned tasks at the same time.
- After a task ends, the assigned member becomes available on the next working
  day.


22. Critical Path Method Details
--------------------------------
The critical path method identifies tasks that directly affect the total
project duration. ScaffoldPM calculates task slack by comparing early and late
schedule values.

Definitions:
- Earliest Start: earliest time a task can begin.
- Earliest Finish: earliest start plus task duration.
- Latest Finish: latest time a task can finish without delaying the project.
- Latest Start: latest finish minus task duration.
- Slack: latest start minus earliest start.
- Critical Task: task with zero slack.

Benefit:
- Helps the project manager identify tasks that require close monitoring.
- Helps detect schedule risks early.
- Helps prioritize management attention.

29. Limitations
---------------
- The generated WBS quality depends on the LLM output.
- The OpenAI API key is required for WBS generation.
- The duration model depends on the quality and relevance of the training
  dataset.
- The scheduler uses a greedy approach and may not produce globally optimal
  schedules.
- Public holidays, leaves, part-time availability, and custom calendars are
  not handled.
- There is no authentication or user management.
- The current repository does not include a completed frontend.
- The database stores lists such as skills and dependencies as comma-separated
  text rather than normalized related tables.
- Dependency cycles are not explicitly handled before NetworkX topological
  sorting.
- File upload limits and malware scanning are not implemented.

33. Suggested Abstract
----------------------
ScaffoldPM is an AI-driven project planning and optimization system designed to
automate the generation of structured project plans from unstructured scope
documents. The system accepts a project scope document and basic project
metadata, extracts clean text, and uses a large language model to produce a
work breakdown structure containing phases, activities, tasks, required skills,
and dependencies. It then applies semantic skill matching to assign tasks to
appropriate team members, estimates task duration using a trained XGBoost model
or heuristic fallback, schedules tasks according to dependencies and working
day constraints, and identifies critical tasks using the critical path method.
The backend is implemented using FastAPI, Pydantic, SQLAlchemy, SQLite,
LangChain, sentence-transformers, XGBoost, and NetworkX. ScaffoldPM reduces
manual planning effort, improves task organization, supports project tracking,
and provides a foundation for future frontend visualization and advanced
optimization features.


34. Suggested Conclusion
------------------------
ScaffoldPM demonstrates how AI and machine learning can be integrated into a
project management workflow to automate planning activities that are usually
performed manually. The system successfully converts project scope documents
into structured WBS data, assigns tasks based on team skills, estimates
duration, schedules tasks, and identifies critical path activities. The modular
backend architecture makes the system maintainable and extensible. Although the
current version has limitations such as lack of authentication, incomplete
frontend support, and greedy scheduling, it provides a strong foundation for an
intelligent project planning platform. Future enhancements can improve the user
interface, scheduling optimization, collaboration, and deployment readiness.


35. How to Run the Backend
--------------------------
1. Move into the backend directory.
2. Create and activate a Python virtual environment.
3. Install dependencies from requirements.txt.
4. Create a .env file containing OPENAI_API_KEY.
5. Start the FastAPI server with uvicorn.

Example command:
uvicorn app.main:app --reload

Expected local API:
- http://localhost:8000

Swagger documentation:
- http://localhost:8000/docs
